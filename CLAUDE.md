# CLAUDE.md — Run & Workout Planner

Guidance for working in this folder specifically. This is a standalone static web app with its own git repo, nested inside the parent Desktop folder — unrelated to `controller_tracker.py` at the top level.

## What this is

Mobile-first static HTML/JS app to plan runs/workouts and log what actually happened (plan vs. actual). No build step, no backend, no framework. Installed as a PWA on the user's iPhone (Add to Home Screen).

## Running it

No install/build needed. Serve the folder and open `index.html`:

```bash
python -m http.server 8791
```

- On this PC: `http://localhost:8791/index.html` (secure context — geolocation and the service worker both work here)
- On the user's phone (same Wi-Fi): `http://<PC's LAN IP>:8791/index.html` — get the IP with `ipconfig | grep IPv4`. This is a plain-HTTP connection, so real GPS and the service worker's offline caching silently no-op there (falls back to IP-lookup/address search for location; PWA install still works over HTTP).

## Files

- `index.html` — shell, tab nav (Upcoming / History), modal host, script tags (classic, non-module — see gotcha below)
- `db.js` — IndexedDB layer. Single `sessions` store. Exposes `window.DB = { uid, Sessions }`. Session shape: `{id, type, title, date, status: "planned"|"completed", planned: {distance, duration, notes, route?}, actual: {distance, duration, effort, notes}}`
- `app.js` — UI logic, tab switching, plan/log/edit/delete forms. Card markup lives in `planCardHtml(s)`/`historyCardHtml(s)`/`sessionCardHtml(s)`, bound via `bindCardActions(container)` — reused by both the Upcoming/History lists and the calendar's day-detail modal, so don't reintroduce inline card HTML elsewhere.
- `calendar.js` — Calendar tab: month grid + week agenda (toggle between them), day-detail modal (`openDayModal`) for viewing/adding/editing sessions by date, with an explicit "← Back to Calendar" button (`.cal-day-header`) rather than relying on backdrop-click to dismiss. **Must load before `app.js` in `index.html`** — `app.js` calls `renderCalendarTab()` at the bottom on init, and classic scripts execute in tag order sharing one global scope, so the reverse order throws a silent unhandled-rejection on first load.
- `routes.js` — IIFE-wrapped map/route builder (Leaflet + OpenStreetMap via CDN). Exposes only `window.openRouteBuilder` / `window.viewRouteModal`. Location fallback chain: real GPS → `locateApprox()` (ipapi.co IP lookup) → static default, plus a Nominatim address search bar (`searchPlace()`). A `userOverride` flag stops the async auto-locate from clobbering a manual search/drawn point after the fact. Also draws a pulsing "you are here" dot (`locationDotIcon()`) once a location resolves, and a 📍 button to re-locate on demand. Route lines/point markers use a custom `routePane` (z-index 650, created via `map.createPane`) so they render above the location dot — Leaflet's default `markerPane` (600) sits above `overlayPane` (400, where vector layers normally live) regardless of add order, so without this the dot always covered the route wherever they overlapped. If the route's first point is placed within 20px (on-screen, via `map.latLngToContainerPoint`, so it works consistently across zoom levels) of the location dot, it snaps exactly onto it; `syncLocationDotSize()` then grows the dot's `locationDotIcon()` from 16px to 24px so it still peeks out from under the route point now drawn on top of it on `routePane`. That size check re-runs on every `redraw()`, so it also un-grows correctly if the snapped first point is undone/cleared. A 🔁 Round Trip toggle in the draw-route footer mirrors the drawn out-leg back to the start and draws it as a thicker dashed overlay (fixed orange `#e0862f`, `lineCap: "butt"` for sharp-edged dashes rather than Leaflet's default rounded caps) on top of the thinner solid green outbound line — the dash gaps let the outbound color show through, so both are visible along the same path. A separate 🎲 Random Route Back button instead fetches a *real, different* street route back via `fetchDistinctReturnRoute(lastPoint, firstPoint, oneWay + 2)`. Asking OSRM for `alternatives=true` was tried first and dropped — its public foot profile rarely offers a genuinely different alternative, so it usually just returned the same path as reversing the outbound leg. Instead this routes *through* a waypoint offset to a random side of the direct line back (`bearingBetween` + the existing `destinationPoint` great-circle helper) — randomized in side, position along the line, and offset size on every try. It tries up to 5 randomized waypoints, discards any candidate over the cap (`oneWay + 4` miles) or flagged by `hasSpur()` (a dead-end there-and-back — two path points far apart in sequence but very close in space, from the synthetic waypoint snapping to an unconnected side street), and keeps whichever survivor has the lowest `outboundOverlapFraction()` (fraction of the candidate's points sampled within ~50m of the outbound path — i.e. "same street"), stopping early once one is under 15% overlap. Deliberately does **not** fall back to the plain direct route on failure — that's exactly the "same street straight back" result this is meant to avoid — so it throws if nothing usable turns up in 5 tries. The button itself always re-rolls on click (no toggle-off state); label switches to "Reroll Route Back" once one is active. The two return-leg options (mirror vs. real reroute) are mutually exclusive — picking one clears the other. `roundTrip` (bool) and `backRoute` (points array or null) are both stored on the saved route alongside the combined `distance`; `viewRouteModal` and the share-card silhouette in `share.js` both render whichever return leg is present.
- `share.js` — IIFE-wrapped "share run" card generator (added 2026-07-31). Exposes only `window.shareRun`. Draws a Strava-style stat card (title, date, distance/time/pace/effort, and a route silhouette if the session has one) to an offscreen `<canvas>`, then hands it to `navigator.share` (native share sheet, e.g. Messages/Instagram on iOS) if `navigator.canShare` supports file sharing, else falls back to downloading the PNG. The route silhouette is a plain white line normalized to the route's own bounding box — no map tiles involved, so it works fully offline. Wired to a "📤 Share" button on completed-session cards in `historyCardHtml` (`app.js`).
- `styles.css` — shared palette with `Personal Dashboard/styles.css` (`--accent: #4a6d5c` light / `#5c9179` dark default) for visual consistency across the user's tools. Theme vars live in `:root`, a `prefers-color-scheme: dark` media block, and `:root[data-theme="dark"]` (explicit override wins). `--accent-soft` (badge backgrounds) is *derived* from `--accent` via `color-mix()`, not a fixed hex — so it stays coherent whether the user is on the default color or a custom-picked one. Any new element using `--accent`-adjacent color needs a `background` set explicitly on inputs/selects/textareas — the browser's native white form-control background does NOT respond to CSS vars alone (bit us once already, see gotchas).
- `manifest.json` / `sw.js` / `icons/` — PWA support (added 2026-07-30). Service worker is same-origin cache-first for the app shell only; map tiles/geolocation/Nominatim calls always pass through to network. Registration is guarded to only attempt on `https:` or `localhost`. **Bump `CACHE_NAME` in `sw.js` any time an app-shell file changes** (currently v29) — the installed iPhone PWA needs a full close-and-reopen (not just a refresh) to pick up the update afterward.

## Backup and Profile (added 2026-07-30)

Both live in the Settings modal (`openSettingsModal()` in `app.js`), modeled loosely on `Health Project/profile.js` but deliberately scoped down — twice, when asked, the user picked the simplest version over the full pattern:
- **Backup**: `exportData()`/`importData()` — downloads/restores all sessions as a JSON file (`Sessions.clear()` + re-`upsert`, a full replace, not a merge). This is the actual answer to "my data only lives on this device" — there's no cloud sync, so this is the only way to carry data across a phone switch or reinstall.
- **Profile**: `localStorage["rwp_profile"]` holds a single `{name, color}` — **not** a multi-profile dict like Health Project's `doh_profiles`/`storagePrefix()`. Purely a cosmetic name+avatar-color badge (`renderProfileButton()` swaps the header gear icon for colored initials once a name is set) — it has no `profileId` concept and never filters or partitions session data. Don't add data isolation here without an explicit new ask; the user has twice declined that scope.

## UI text casing: Title Case for chrome, sentence case for prose

Static UI *chrome* — labels, buttons, headings, tab names — is Title Case with every word capitalized literally (no small-word exceptions for "a"/"on"/"to"; e.g. "Draw Route On Map", "Back To Calendar"). Content inside parentheses is left as-is (`(min)`, `(mi)`, `(1-10)`). This does **not** extend to actual prose: hint paragraphs (the backup/import blurb), confirm/alert dialogs ("Delete this session?"), status messages in `routes.js` ("Finding your location…"), empty-state one-liners ("Nothing planned yet."), or input placeholders — those stay normal sentence case since Title-Casing a full sentence reads oddly. When adding new static UI text, match whichever category it falls into.

## Duration format: "min.ss", not decimal minutes

Duration inputs (`Target Time (min)` on the plan form, `Duration (min)` on the log form) accept `mm.ss` — the digits after the dot are literal seconds, e.g. `45.30` = 45 min 30 sec, not 45.3 decimal minutes. Parsing/formatting lives in `app.js`: `parseMinSec(str)` → decimal minutes (for storage, with correct 60-sec rollover), `formatMinSec(mins)` → `mm.ss` string (for pre-filling the input on edit), `formatDuration(mins)` → `"m:ss min"` (for card display). Sessions still store plain decimal minutes internally, so `pace()` and existing whole-number data need no changes. Duration inputs are `type="text" inputmode="decimal"`, not `type="number"` — custom parsing means native number-input semantics don't apply, and it avoids the `step` mismatch class of bug below.

## Theming (dark mode + custom accent color, added 2026-07-30)

Settings live behind the gear icon in the header (`#settings-btn` → `openSettingsModal()` in `app.js`), not a direct toggle. Two independent choices, both in `localStorage` and both applied via an inline `<script>` in `index.html`'s `<head>` **before** `styles.css` paints (avoids a flash of the wrong theme):
- `theme` — `"light"` / `"dark"`, sets `data-theme` attribute on `<html>`. No explicit choice → follows system `prefers-color-scheme`.
- `accentColor` — hex string from a native `<input type="color">`, applied as an inline `style.setProperty("--accent", ...)` on `<html>` so it overrides the stylesheet's theme-based default regardless of light/dark.

If adding new themeable UI, use CSS vars (`--bg`, `--panel`, `--border`, `--text`, `--text-dim`, `--accent`, `--accent-soft`, `--danger`, `--workout-soft`, `--workout-accent`) — never a hardcoded hex — or it won't respond to dark mode or a custom accent.

## Testing

**User tests changes themselves now (as of 2026-07-30) — don't run claude-in-chrome browser-automation testing on this project unless explicitly asked.** Ship the code change and report it's done. The full spin-up-a-server-and-click-through-the-UI testing loop was adding real time to small changes without proportional value once the app's core patterns were already established and verified. Fine to sanity-check logic directly (e.g. call a function in isolation) if genuinely uncertain about correctness.

## Known gotchas (already hit and fixed — don't reintroduce)

- `db.js` and `app.js` load as classic `<script>` tags sharing one global scope. Don't re-declare `const { Sessions, uid } = window.DB` in `app.js` — those names are already global from `db.js`; redeclaring collides.
- Any numeric `<input>` that gets a value from something other than direct typing (e.g. route-computed distance with 2 decimals) needs `step="any"`, not `step="0.1"` — mismatched step blocks form submission via native HTML5 validation with **zero console output**. Looks like "Save does nothing."
- Real GPS and the service worker both require a secure context. This app is normally accessed over plain HTTP via LAN IP on the phone, so both degrade gracefully by design — don't "fix" this by chasing HTTPS unless the user brings it up. **Local HTTPS/mkcert was tried and explicitly abandoned by the user** (alarmed by running an unfamiliar binary against the Windows trust store) — do not revisit unless they explicitly ask again.
- `.modal input/select/textarea` need an explicit `background: var(--panel)` — without it they inherit the browser's native white form-control background regardless of any `color` CSS var, producing near-invisible light-on-white text in dark mode. Any new form-control CSS in this project must set both `color` and `background` from vars.
- `.modal input::placeholder`/`.modal textarea::placeholder` are dimmed (`var(--text-dim)`, 0.65 opacity, italic) so example text like "e.g. 45 or 45.30" reads clearly as a hint rather than something already typed — added 2026-07-31 after this looked too similar to real input. Don't rely on the browser's UA-default placeholder styling for new inputs; it isn't dim enough against this app's custom `--panel` backgrounds.
- **Testing gotcha, not a code bug:** when iterating on files and testing via claude-in-chrome against a long-lived `python -m http.server` port, the *browser's plain HTTP cache* (not the service worker — that's a separate, already-understood issue) can keep serving stale JS/CSS across normal navigations indefinitely, even after unregistering the SW and clearing Cache Storage. `curl` to the same port confirms the server has fresh content. Fastest fix: bump to a brand-new port for that test session rather than debugging the cache.
